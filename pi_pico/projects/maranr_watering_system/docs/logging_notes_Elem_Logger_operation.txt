How logger_elem package's modules are used.

Consider an object instance of class X that logs messages (i.e., lines,
i.e., instances of str).
It uses the log functions that are module-global variables in its X module.
Those variables are given values by the X._set_logger() method, which
is an abstract method defined in class X. Each such variable is a reference
to a function that takes one str and logs in to a 'current' log file.

Every such class X must inherit from abstract base class ('ABC'),
namely ElemLoggerABC. 
This ABC has its __init__ invoked from each child class X.__init__ 
when an instance of class X is created. The ABC __init__ obtains a 
reference ('elc') to the singleton instance of ElemLogControl; it uses that
reference to call elc.register_user_class(self) - where 'self' refers
(obviously) to the instance of X (and so to its parent ElemLoggerABC).
This allows ElemLogControl ('ELC') to keep a registry of all classes that 
wish to perform logging. Every instance of class X gets the same
ElemLogger. Typically there is only once instance of any class X,
but there can be more than once instance. The enabled/disabled state
of the ElemLogger affects all instances of class X.

Currently the ELC is implemented as a singleton.

In addition to maintaining a registry of objects doing logging,
the ELC provides a suitable instance of ElemLogger (the 'logger')
to each ABC instance. The ABC uses the methods of this 'logger' in
order to inject bound methods from logger into the module-global variables
of X. The ElemLogger instance is created by ELC and is provided
a reference back to the ELC. This allows the ElemLogger to access
the ELC.log_one_line() method, providing the means to log a line
to a log file. Because the log,logrt, and logi are module-global,
creating a new instance of X rebinds them in the X module.
Because every instance of X uses these global functions, all 
extant instances of X will start using the new logger.

When X invokes log("log mesg"), it calls the bound method 'log' from
its ElemLogger (i.e., the value associated with the module-global
variable). The bound method of ElemLogger in turn calls an
appropriate logging method ('log_one_line') on ElemLogControl.

When ElemLogControl is instantiated (again, as a singleton),
it creates an instance of ElemLogFileTable ('elft'). 
This elft instance manages the creation and deletion of log files
as well as providing a method 'log_one_line' that writes one
line (str) into the currently-active log file (and creates such a file,
if needed, including rotation to a new file if that is needed).
The ElemLogControl.log_one_line method uses the elft.log_one_line()
method to write the line (str) to the log.

For testing purposes, ElemLogControl includes a class method 
'_nullify_instance()' which removes the singleton instance from
its class-level attribute _instance. (This is where the singleton
reference to the ElemLogControl is stored.) In doing so, it leaves any
extant ElemLoggerABC and ElemLogger instances (and so any extant X 
instances) with a reference to the 'old' ElemLogControl.
This 'old' instance holds a reference to its ElemLogFileTable
instance, which is managing the log files.
All of the extant instances of X can therefor continue to perform logging.
Under normal circumstances, both production and unit testing, 
a single instance of ElemLogControl is created and held.
The _nullify_instance() is not normally called - so may be eliminated(?)
There is a TBD function that will 'clear out' most of the contents
of the ElemLogControl. But it will probably leave the registry
as is, but go through the registry and remove existing loggers(?)

UPDATE:
Per-name enable_logging works before the class registers.
The ELC has a dict mapping class-name to log-enabled state.
This is applied at registration. 
This means a per-class setting of the log-enabled state is known
even before a class tries to register itself for logging; this allows
the correct log-enabled state to be applied to it when it registers.
The dict is kept for the life of the process; a per-test reset empties it 
and sets every registered logger’s enabled flag back to the default.

If another test creates another ('new') instance of X, a new
singleton instance of ElemLogControl will be created along with 
a new ElemLogFileTable instance. The latter will begin trying to
create new log files to receive logged lines from objects
such as X (and other object instances) as these start
performing logging function calls. This obviously can cause 
collisions in the file space as the two instances of 
ElemLogFileTable will be unaware of each other.

It is important then that every test ensures that any and all
object instances of X and other such classes that perform logging 
are no longer active. This can be an issue of a class that performs 
logging exists as a singleton: the singleton instance must be 
discarded ('nullified') if a second test on that class is performed.
A singleton (of a class that logs) that is 'left over' from a previous 
test would continue to log using the 'old' logger objects and hence the
'old' log file directory and files.

In addition, it is very desirable for the unit test facility to ensure 
that the logging subsystem does not attempt to log into the production
logs directory - to avoid polluting 'real' production logs with
logs created by testing. This is achieved by having the unit test
'glue' facilities set up / configure the logging facility such that the
latter enters a 'testing' mode which causes it to always write to
logging directorie(s) that are distinct from the production directory.
Such a mode would be implemented to strictly preclude execution path that 
could cause it to fall back to writing to the production logs directory.

Creating ElemLogControl or ElemLogFileTable never touches the logs dir.
The logs dir is created and scanned only inside log_one_line(), 
which in turn calls _start_a_new_logfile() which in turn creates the
log dif (if not yet extant) and determines the name of the first
log file that the current process will use. Thus the logs dir
is created in a very lazy fashion; this helps ensure that 
the ELC is created and configured well before any logging is done.

The ELC provides a method:
   enable_logging(self, class_name: str, enabled: bool) -> None:
that is used by the webserver RequestHandlerLog. It allows a web user
to turn logging on and off (enable/disabled) on an individual class basis.

Current implementation notes:
- lazy open on the first line logged
- a flush is performed after every line is logged
- log file names take the form mws_log.NNN where NNN is 010 ... 999
- each new program execution finds a suitably large NNN for its first
  log file name, so that prior log files are not overwritten.
- logs are rotated when they reach a size of 25,000 bytes
- the logger removes log files if the high watermark and continues
  removing until the total size of the remaining/extant log files
  goes to or below the low water mark. Oldest files are removed first.
- ElemLogControl.get_lines_from_log_file() allows the 'log' page within
  the webserver to obtain specified lines from the currently-active 
  log file.
